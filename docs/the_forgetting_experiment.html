Part 1

Machine learning basics

You need five ideas to follow everything else on this page. Each one is used directly in your code.

What a neural network is

A neural network is a function with a lot of adjustable numbers inside it. You give it an input (here, a 28 × 28 pixel image of a handwritten digit, which is 784 numbers between black and white) and it gives back an answer.

The adjustable numbers are called weights. Your MNIST model has about 480,000 of them. The network multiplies the 784 pixel values by weights, adds them up, passes them through a simple bend (a rule that turns negative numbers into zero), and repeats that through two layers of 400 units each. At the end come 10 output numbers, one per digit.

Those 10 outputs are called logits. They are scores: the biggest one is the network's guess. If logit number 7 is the largest, the network is saying "this is a 7".

When the network is new, its weights are random, so its guesses are random: about 10% right. Learning means changing the weights until the right logit tends to be the largest.

How training works

Training is a loop. Each turn of the loop:

  1. Take a batch of 64 images with their correct labels.
  2. Run them through the network and get its guesses.
  3. Measure how wrong it was with a single number called the loss. We use cross-entropy loss: it is small when the network gave a high score to the right digit and large when it was confidently wrong.
  4. Work out, for every weight, which direction would make the loss a bit smaller. That set of directions is the gradient. PyTorch computes it automatically.
  5. Move every weight a small step in that direction. The size of the step is the learning rate (0.01 in your project).

One pass of this loop is a training step. One pass over all of a lesson's images is an epoch. Your MNIST setup uses 2 epochs per lesson, which is about 340 steps per lesson and 1,694 steps in total.

This method is called gradient descent: picture the loss as a landscape and the training as walking downhill. Try it below. The curve is the loss for a single weight, and each step moves the weight downhill by learning rate × slope.

Try it · gradient descent on one weight
weight -1.00 · loss 16.00 · step 0

With a small learning rate the dot creeps down slowly. Around 0.5 it lands in one step. Above 1.0 every step overshoots further than the last and the weight flies off. That is exactly the bug you hit with EWC: its penalty made some weights so "steep" that each step overshot, and the weights blew up to NaN ("not a number"). The fix capped the steepness so that one step can never overshoot.

Training data, validation data and test data

A network can memorise its training images without learning the general idea of a "3". So you always check it on images it has never trained on. Your project keeps four separate piles of data for each lesson:

Train
About 90% of the lesson's images. The only data the network learns from.
Judge
40 held-out images per lesson. Only your method's judge uses them, to decide whether to undo an update. They count against its memory budget.
Validation (val)
The rest of the held-out images. Used to choose settings, such as EWC's penalty strength or your method's sleep length.
Test
The official MNIST test images. Only used to report final numbers, never to choose anything.

Why the separation matters. If you pick settings by looking at test scores, you are quietly fitting to the test set, and your reported number is too optimistic. Every choice in this project was made on validation data.

Catastrophic forgetting

Now the actual problem. Train the network on lesson 1 (0 vs 1) and it scores almost 100%. Then train it on lesson 2 (2 vs 3). Every training step now only looks at 2s and 3s, so the gradient only cares about getting 2s and 3s right. Nothing in the loop knows or cares why the weights had their old values. The weights that made it good at 0s and 1s get overwritten.

In your first run the result was total: after each new lesson, accuracy on every earlier lesson dropped to 0.0%. This is called catastrophic forgetting, and stopping it is the whole field of continual learning.

Two versions of the test

  • Class-incremental (the hard one, your main test). At test time the network must pick from all 10 digits and is not told which lesson an image came from.
  • Task-incremental (the easy one). The network is told "this image is from lesson 3", so it only has to choose between 4 and 5. Almost every method scores 98–99% here, so it can't separate good methods from bad ones.

Measuring forgetting

After each lesson, you test on every lesson seen so far and write the scores in a grid. Row = "after training on lesson N", column = "score on lesson M". This is the accuracy matrix. Two numbers summarise it:

  • Final average accuracy (ACC): the average of the last row, the score on all 5 lessons at the end. Higher is better.
  • Forgetting: for each old lesson, the best score it ever had minus its final score, averaged. Lower is better.

Every file, explained

cl/data.py105 lines

Downloads the dataset and cuts it into 5 lessons of two classes each. Each lesson gets the four piles described earlier: train, judge, val and test. Everything is loaded into memory at once, since MNIST is small. It now also handles CIFAR-10 (colour photos) for the harder test.

tasks = make_split("mnist", seed=0)
tasks[0]   # Task 0 classes=(0, 1) train=11399 judge=40 val=1226 test=2115
cl/model.py67 lines

The networks. MLP is the MNIST network: 784 inputs, two layers of 400, 10 outputs. ReducedResNet18 is a small image network for CIFAR-10, the same one used in published continual-learning papers. Both have a single 10-way output shared by all lessons.

cl/metrics.py75 lines

Scoring. evaluate measures accuracy on a set of images. It also builds the accuracy matrix and computes final average accuracy and forgetting. active_logits switches between the hard and easy versions of the test: in the easy one it hides the scores for digits outside the current lesson.

cl/strategies.py286 lines

The shared training loop plus the baseline methods. The loop has five hooks, places where a method can change behaviour:

  • before_task: set up before a lesson (for example a fresh optimizer)
  • make_batch: change the batch (replay adds old examples here)
  • extra_loss: add to the loss (EWC adds its penalty here)
  • after_step: after each step (replay saves examples here)
  • after_task: after a lesson (EWC measures weight importance here)
for batch in lesson:
    xb, yb = self.make_batch(x, y, task)                    # hook
    loss = self.task_loss(xb, yb, task) + self.extra_loss(xb, yb, task)
    loss.backward(); optimizer.step()                       # gradient descent
    self.after_step(x, y, task)                             # hook

Methods in this file: Naive, Replay, EWC and DERPP (DER++).

cl/ours.py416 lines

Your method. It is long because it does a lot: surprise gating, two memories, sleep, the judge with undo, and targeted replay. Each part has an on/off switch (use_surprise, use_sleep, use_judge, use_targeted), so it can be tested with one part removed. It checks after every change that it never stores more than 500 examples in total.

run_experiment.py165 lines

The command you actually run. It picks a method, trains it on the 5 lessons in order, tests after each lesson, prints the accuracy matrix, and saves everything to results/<method>_<scenario>.json. Flags choose the dataset, method, number of runs (--seeds), and settings (--hp key=value).

run_suite.py147 lines

Runs the whole second round of experiments unattended: tuning DER++ on validation data, compute-matched baselines, and the CIFAR-10 benchmark. It runs MNIST on the CPU and CIFAR on the GPU at the same time and logs progress to results/suite_progress.log.

make_report.py288 lines

Reads every results file and produces results/summary.md (the tables), avg_acc.png (score after each lesson) and forgetting.png (final scores side by side).

results/

One JSON file per method and test. Each holds the accuracy matrix for every run, the summary numbers, and stats such as training steps and rollbacks. sweep_* folders hold tuning runs on validation data.

Running it yourself

From the continual_learning folder:

# one method, 3 runs, hard test
.venv/bin/python run_experiment.py --strategy replay --seeds 0 1 2

# your method with the judge switched off
.venv/bin/python run_experiment.py --strategy ours --hp use_judge=False --tag no-judge

# rebuild the table and charts
.venv/bin/python make_report.py

A full 5-lesson MNIST run takes 2 to 10 seconds on your Mac's CPU.

Part 3

The experiment

The methods we compared

MethodIdea in one line
NaiveJust keep training. The "no protection" baseline.
ReplayKeep a notebook of 500 random old examples; mix 64 of them into every batch.
EWCMeasure which weights mattered for old lessons and penalise moving them.
DER++Replay, but also remember the network's old output scores and keep them the same. Added in round two.

Why EWC fails the hard test. EWC protects old weights, but the final layer still only ever sees new digits during training, so it learns to always score new digits highest. Old lessons drop to 0% anyway. Replay works because old digits keep appearing in training, so the final layer keeps learning to tell old from new. This is a known result from published research, not a bug in your code.

Your method

Five parts that work together, loosely inspired by how brains are thought to learn:

Surprise gating
use_surprise

Compute each example's loss. Only learn from and store the ones that are unusually wrong.

Two memories
fast buffer + long-term

A 50-slot short-term notebook of recent surprising examples, and a balanced long-term store of old lessons.

Sleep
use_sleep

Every 25 steps and at the end of a lesson, pause and do 10 steps of mixed new + old review.

Judge with undo
use_judge

After each sleep, quiz old lessons on the judge sets. If any lesson lost more than 3 of 40, restore the saved weights and retry with more review.

Targeted replay
use_targeted

Review slipping lessons more often than stable ones.

The undo, step by step

  1. Save a full copy of the weights and the optimizer's memory of recent steps.
  2. Train: wake steps, then a short sleep.
  3. Judge quizzes every old lesson on 40 images each.
  4. If an old lesson dropped by more than 3 correct answers, throw away the new weights and restore the copy. Retry with twice as much old-lesson review.
  5. After 2 failed retries, accept anyway. Otherwise the network could never learn the new lesson.

Fair comparison. Your method gets exactly the same 500-example memory as replay, and the judge's 40 images per lesson count toward those 500. It cannot win just by remembering more.

The trade-off hidden in the grid

Look at the last row of your method's matrix above: it scores only 85.8% on the newest lesson, where replay scores 97.5%. The judge keeps rejecting updates that hurt old lessons, which also slows down learning the new one. Holding on to old knowledge versus taking in new knowledge is called the stability–plasticity trade-off, and your method leans towards stability.

The cost

Your method uses 1.7× the training steps of the baselines (2,824 vs 1,694), and the judge undoes about 43 updates per run, throwing away roughly 45% of the steps it took. The tuning agent gave replay 2.5× more training and it did not improve, so the extra compute alone doesn't explain the gap. A cleaner compute-matched test is running now.

Which parts matter

An ablation removes one part and reruns. If the score drops, that part was doing work. Hard test, 3 runs each:

Ablations · final accuracy on the hard test
80%90%
  • Judge and sleep do the real work. Removing either costs 1.8 to 3 points and doubles forgetting.
  • Surprise gating and targeted replay don't clearly help. Their effect is smaller than the run-to-run noise.

Bugs we caught

A reviewer agent tried to break the method before any final numbers were recorded. It found four real problems, all fixed:

  • Broken undo. PyTorch's optimizer kept sharing memory with the saved copy, so a second undo in a row didn't fully go back. Fixed by deep-copying the saved state.
  • Misleading "no sleep" test. With sleep switched off, the retries still ran sleep-like training, so that ablation wasn't really removing sleep.
  • Rounding error. The judge compared decimal fractions such as 1.0 − 0.95 against 0.05, which floating-point maths gets wrong. It now counts correct answers as whole numbers.
  • Surprise gating barely did anything. Almost none of the surprising examples it picked out ever reached long-term memory.

Plus the EWC overshoot bug from Part 1, which you can reproduce in the gradient-descent demo.

Is it new?

Not really. Each part has been published before:

  • Surprise-based memory: InfoRS (2022) and SuRe (2025).
  • Fast and slow memories: CLS-ER (2022).
  • Sleep consolidation: Wake-Sleep Consolidated Learning (2024).
  • Targeted replay: MIR (2019).
  • Judge with undo: the least common part. GEM and A-GEM block harmful steps instead of undoing them.

On this benchmark, published simple replay scores about 87% and DER++ about 92%. Your method's 89% sits between them. So the next step was to run DER++ in the same code, under the same rules.

Round 2: DER++ and CIFAR-10

Round 2 added three things:

  • DER++, the stronger rival from the research. It's replay that also remembers the network's old output scores for each stored example and trains it to keep producing them, so it remembers how confident it was about every class, not just the right answer. Same 500-example memory.
  • Compute-matched baselines. Replay and DER++ also ran with more epochs, so they took more training steps than your method. That rules out "it just trained longer".
  • Split CIFAR-10: colour photos (airplane, car, bird, cat, deer, dog, frog, horse, ship, truck) in 5 lessons of two classes, using a small ResNet image network. It ran on a free Kaggle GPU. Papers train 50 passes per lesson; this used 5, so absolute scores are lower than published ones. Only the comparison between methods counts.

Your method never learns the new lessons well. Forgetting is measured from a lesson's best score, and a lesson that only reached 50% has little to lose. The judge keeps undoing updates that hurt old lessons, and those same updates are how the new lesson gets learned. This is the stability–plasticity trade-off tipped too far towards stability.

The judge still matters: without it, your method collapsed to naive level (17–18%) on 2 of 3 runs and got lucky on the third (38%). Its real job on CIFAR is preventing collapse.

One fairness caveat. The learning rate and DER++'s settings were tuned on CIFAR validation data, while your method kept its MNIST settings. That favours DER++, though probably not by 10 points.

Round 3: relaxing the judge

If the judge is too strict, loosen it. Four ways were tested: the first was already a setting, and the other three are new switches, all off by default.

  • Allow bigger drops: reject only when an old lesson loses more than N of its 40 judge images (normally 3).
  • Average, not any: reject only when old lessons dropped a lot on average, rather than whenever a single one slipped.
  • Stop judging once learned: when the new lesson reaches a target accuracy, stop judging for the rest of it.
  • Trade-off rule: also accept an update if what it gained on the new lesson outweighs what it cost the old ones.

MNIST: it works as designed, but there was little to gain

Relaxing raised the new-lesson score from 94.6% to as high as 98.9%, but forgetting rose faster. The best setting (allow 5 of 40) reached 89.6% ± 0.7 on test data, up from 89.1% and level with DER++'s 89.9%. All three are tied within noise.

"Stop judging once learned" never helped: every threshold scored below the strict judge, because it let forgetting back in for the rest of each lesson.

CIFAR-10: relaxing doesn't help

Six judge settings were tuned on CIFAR validation data. The best ("allow 8 drops") scored 27.9% ± 2.4 on test data, against the strict judge's 28.6%. The top four settings were within half a point of each other, which is just noise, and new-lesson scores barely moved (65% → 66%).

The real cause: the undo throws away new learning

The run statistics showed what's happening. On CIFAR the judge rejects almost every update: about 226 undos per run, against 43 on MNIST. Each undo restores the saved copy of the network, and that also discards everything it just learned from the new lesson's images. The retry then only practises on the few hundred examples held in memory.

RunTraining steps on new imagesThrown away by undos
MNIST, strict judge1,69450%
CIFAR-10, strict judge3,52580%
CIFAR-10, allow 8 drops3,52580%

So four fifths of each new lesson's training is discarded, which is why new lessons stall around 65%. Loosening the threshold can't fix that: learning new classes always costs old classes something, and on CIFAR that cost is bigger than even 8 of 40. The 40-image quiz is also noisy, swinging by about ±3 correct answers by chance alone.

What this suggests. The judge should guard old lessons without throwing away new learning. For example, the undo could restore only the sleep phase and keep the training on new images, or the retry could also practise on new images.

Glossary

Weights
The adjustable numbers inside a network. Learning changes them.
Logits
The network's 10 output scores, one per class. The largest is its guess.
Loss
One number measuring how wrong the guesses were.
Gradient
For each weight, the direction that reduces the loss.
Learning rate
How big a step each update takes.
Batch / step
A group of 64 examples, and one update using them.
Epoch
One pass over all of a lesson's training images.
Optimizer
The code that applies the updates. Ours (SGD with momentum) also remembers recent steps, which is why the undo must restore it too.
Seed
A number that fixes the randomness, so a run can be repeated exactly. "3 seeds" means 3 independent runs.
Baseline
A standard method to compare against.
Ablation
Rerunning with one part removed, to see what it contributes.
Hyperparameter
A setting chosen by you rather than learned, such as learning rate or sleep length.
Stability–plasticity
The trade-off between keeping old knowledge and learning new knowledge.
